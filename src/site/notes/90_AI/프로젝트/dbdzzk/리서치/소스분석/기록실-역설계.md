# 기록실 역설계 — 소스가 없다

> **`dbd.jetack.com`은 공개 저장소가 없다.** GitHub 검색(`jetack`, `내전 기록실`, `chzzk dbd`) 전부 무소득이고, 사이트·번들 어디에도 저장소 링크가 없다. 셋 중 유일하게 닫혀 있다.
>
> 대신 **공개 REST API가 인증 없이 전부 열려 있어** 데이터 모델과 알고리즘 파라미터를 그대로 읽을 수 있다.

## 프론트 번들에서 확정되는 것

배포 청크 이름이 도메인을 그대로 드러낸다.

```
index · routes · games · edgeCache · scrimWrites
kills · board · killerStats · popover · badge · button
compiler-runtime · react-dom · sonner · createLucideIcon
useRenderElement · useBaseUiId · useButton · composite · useScrollLock
```

- `compiler-runtime` → **React Compiler**를 켰다
- `useRenderElement`·`useBaseUiId`·`composite` → **Base UI** (치바데·치즈스톰도 같은 라이브러리를 쓴다)
- `react-router` / `react-router-dom` 문자열이 `routes` 청크에 있다
- `edgeCache`·`scrimWrites`가 **별도 청크로 잘려 있다** — 캐시 계층과 쓰기 경로를 의식적으로 분리했다는 뜻
- `recharts`·`d3`·`chart.js`·`visx`·`nivo` **전부 0건** → 레이팅 추이 그래프는 자체 SVG

## 백엔드가 Go라는 근거

HTML 주석에 개발자가 직접 써 뒀다.

> The commit this bundle was built from. Substituted by Vite from `VITE_BUILD_SHA`, which the Dockerfile hands to **BOTH build stages**; **the Go binary carries the same value.** See `lib/appVersion.ts`.

```
GET /api/version → {"build":"6d9b469","frontend":"6d9b469"}
```

**프론트와 백엔드가 같은 커밋 SHA를 들고 다니며 불일치를 감지한다.** 멀티스테이지 Docker 빌드로 Go 바이너리에 정적 프론트를 함께 넣는 구조.
응답 헤더는 `server: cloudflare` · `cache-control: public, max-age=3` — **엣지 3초 캐시**. 진행 중 내전 화면을 폴링해도 오리진이 안 터지는 값이다.

## 레이팅 파라미터 — `meta`가 다 말해준다

`/api/leaderboard`와 `/api/players/{id}` 응답에 공통으로 붙는다.

```json
{
  "ratingBase": 1500,
  "drawKills": 2,
  "minGamesToQualify": { "killer": 5, "survivor": 20 },
  "takenAt": "2026-08-31T23:08:58Z",
  "previousTakenAt": "2026-08-30T23:00:00Z"
}
```

여기서 확정되는 것:

1. **기준 레이팅 1500** — 치즈스톰 `INITIAL_ELO`와 같은 관례
2. **`drawKills: 2`** — 4명 중 2명 탈락 = 무승부. 그래서 4v4 통계 안내문의 "연장승부는 무승부로 처리되며, 승률 계산시 0.5승"이 성립한다
3. **자격 최소 경기수가 포지션별로 다르다** — 킬러 5경기 / 생존자 20경기. 4v4에서 한 사람이 킬러를 도는 빈도가 생존자로 뛰는 빈도의 1/4이라 분모를 맞춘 값
4. **`takenAt` / `previousTakenAt`가 정확히 23:00 UTC(= 08:00 KST)** — **레이팅을 하루 한 번 스냅샷으로 굳힌다.** 랭킹의 `delta`와 ▲▼ 화살표는 어제 스냅샷 대비 변화다

> [!important] 스냅샷이 알고리즘 변경을 흡수한다
> 공지에 "레이팅 알고리즘 일부 수정"(08-14), "점수 미세조정"(08-24)이 있다. 매 요청마다 재계산하는 구조였다면 알고리즘을 고칠 때마다 순위가 요동쳤을 것이다.
> 일일 스냅샷 + `takenAt` 명시 + 티어표 버전 선택 — **재계산 가능한 지표를 다루는 세 겹의 장치**다.

선수 레코드 구조:

```
player { id, name, chzzkChannelId, chzzkUrl, avatarUrl, active, createdAt }
total, totalRadius, totalDelta, games
killer   { rating, radius, delta, games, wins, draws, losses, killDist[5], winRate }
survivor { ... 동일 ... }
modes  { "4v4": { all: { killer, survivor, rounds } }, "5p": { all: { killer, survivor } } }
ladders{ "4v4": { killer, survivor, total, totalRadius, totalDelta }, ... }
```

`radius`는 Glicko의 RD와 같은 역할(불확실성 반경)을 하지만 **번들·API 어디에도 `glicko`·`volatility`·`deviation` 문자열은 없다.** 자체 구현으로 보인다 — 단정하지 말 것.

## 원탁 티어표 (`/api/tiers`)

```json
{ "lists": [{
  "name": "원탁", "author": "울프", "authorId": 7,
  "authorChzzkChannelId": "0b33823ac81de48d5b78a38cdbc0ab94",
  "versions": [{
    "id": 1, "announcedAt": "2026-08-04T21:00:00Z", "zeroLabel": "꿈나무",
    "killer":   { "<playerId>": 0~12 },
    "survivor": { "<playerId>": 0~12 }
  }, ...]
}]}
```

- 티어표가 **1급 엔티티**다 — 이름·작성자·치지직 채널까지 붙는다. `lists` 배열이라 **원탁 말고 다른 티어표도 얹을 수 있는 구조**
- 버전마다 `announcedAt`이 있고 **킬러 점수와 생존자 점수를 따로 매긴다**
- `zeroLabel: "꿈나무"` — 0점 밴드에 별칭을 붙인다. 화면의 "꿈나무"가 이것
- 자동 계산이 아니라 **사람이 매긴 점수**다. 레이팅(자동)과 티어표(수동)를 분리한 셈 — 치즈스톰 ADR-0005와 같은 결론에 도달했다

## 살인마 통계 (`/api/killers`)

44종. 치바데의 CSV 카탈로그와 **정확히 같은 44개**다.

```
killers[] { name, formats: { "4v4" | "all": { games, killDist[5], pickRounds, banRounds, players[] } } }
formats   { "4v4": { games: 611, pickRounds: 90, banRounds: 14 }, "all": { games: 683, ... } }
```

**픽률·밴율의 분모를 응답이 직접 들고 온다.** 화면의 "픽률은 킬러가 기록된 90개 라운드, 밴율은 밴이 기록된 14개 라운드 기준"이 하드코딩 문구가 아니라 데이터에서 나온 값이다.

## 경기 레코드

```json
{ "id": 1049, "playedAt": "...", 
  "killer": { "playerId": 19, "name": "실프" },
  "survivors": [{ "playerId": 15, "name": "둥그레" }, { "playerId": 32, "name": "눈꽃", "slot": 1 }, ...],
  "kills": 3, "outcome": "killer_win", "killerChar": "퍼스트",
  "source": "helper",
  "scrim": { "scrimId": 96, "roundNo": 1, "kind": "main", "seq": 3, "team": 0, "roundGames": 10 } }
```

- **한 판(round)이 아니라 한 경기(game) 단위**로 저장한다. `scrim.seq`가 라운드 내 순번, `roundGames`가 그 라운드의 총 경기 수
- `kind: "main"` → 본선/에결 등 구분이 있다
- `team: 0|1` → 4v4에서 어느 팀이 살인마였는지
- `source: "helper"` → **진행 도구 유입.** 시청자 수기 입력과 구분하는 필드

## 정리 — 소스 없이도 읽히는 설계

| 관측 | 결론 |
|---|---|
| `/api/version`이 프론트·백 SHA 비교 | 배포 불일치를 런타임에 잡는다 |
| `edgeCache`·`scrimWrites` 청크 분리 | 읽기 캐시와 쓰기 경로를 의식적으로 갈랐다 |
| `max-age=3` | 실시간처럼 보이되 오리진 부하는 3초에 한 번 |
| `takenAt` 일일 스냅샷 | 알고리즘을 고쳐도 순위가 요동치지 않는다 |
| `minGamesToQualify` 포지션별 분리 | 킬러/생존자 출전 빈도 차이를 알고 있다 |
| `source: "helper"` | 데이터 출처를 레코드가 스스로 증언한다 |
| 티어표가 `lists[]` | 티어표를 여러 개 얹을 여지를 남겼다 |
