## 1. 레이팅 — 세 곳이 전부 1500에서 시작한다

| | 기록실 | 치즈스톰 | dbdzzk |
|---|---|---|---|
| 기준값 | `ratingBase: 1500` | `INITIAL_ELO = 1500` | `START_RATING = 1500` |
| 단위 | 킬러/생존자 **분리** | 팀 평균 vs 팀 평균 | 킬러/생존자 **분리** |
| 등락폭 | (비공개) | 로지스틱 `MAX_DELTA=40`, 대등 ±20 | `K_KILLER = K_SURVIVOR = 16` |
| 불확실성 | `radius` 필드 노출 | 없음 | 없음 |
| 풀 분리 | `ladders: 4v4 / 5p` | 없음(단일) | **포맷별 풀 분리** |
| 대회/특수 제외 | `kind` 필드 존재 | **ADR-0022 대회 제외** | — |

### 무승부 정의가 같다

```
기록실:  "drawKills": 2                       (API meta)
dbdzzk:  kills / 4 → 2킬이 무승부 0.5          (src/lib/elo.js)
```

4명 중 2명 탈락 = 0.5. **두 프로젝트가 독립적으로 같은 수치를 골랐다.**

### K값을 낮춘 이유도 같은 문장이다

dbdzzk `elo.js` 주석:

> 체스는 경기당 32를 쓰지만 우리는 판마다 갱신하고 내전 한 번에 8판이 돈다 — 32면 생존자가 하룻밤에 ±100 이상 흔들려 **어제와 오늘의 티어가 달라진다.**

치즈스톰 `elo.ts` 주석:

> 내전은 밸런싱돼 기대승률이 30~70%에 몰리므로 그 구간을 가파르게, 바깥은 완만하게(포화) 만들어 이변에 크게·강팀 압승에 작게 반응시킨다.

둘 다 **표준 K=32가 내전에는 너무 크다**는 결론. 해법만 다르다 — dbdzzk는 K를 절반으로, 치즈스톰은 K 자체를 곡선으로 바꿨다.

### 경로 의존 타이브레이커 — 같은 버그를 같은 방식으로

```
치즈스톰 f3a3875  "Elo 계산에 같은 날 경기 순서 타이브레이커 추가"
  date는 시각 없는 자정값이라 같은 날 경기끼리 동점 → createdAt(입력 순)으로 확정.
  Elo는 경로 의존적이므로 이 타이브레이커가 없으면 최종 레이팅이 문서 ID 순에 좌우된다.

dbdzzk  a2e82db  "elo 재생 결정성 강화 — playedAt 동시각은 roomCode로"
  같은 타임스탬프의 경기가 둘 이상이면 배열 순서에 따라 결과가 갈리는 경로 의존 버그가
  생긴다(누적되면 Elo가 맞밸 짝을 조용히 바꿔버린다).
```

**완전히 같은 버그, 완전히 같은 해법.** dbdzzk는 여기서 한 걸음 더 갔다 — `playedAt`이 숫자가 아니면 `throw`한다("조용히 티어가 틀어지는" 대신 시끄럽게 죽인다).

### 최소 표본을 포지션별로 다르게 잡는 것도 같다

```
기록실:  minGamesToQualify = { killer: 5,  survivor: 20 }
dbdzzk:  MIN_KILLER_ROUNDS = 3, MIN_SURVIVOR_ROUNDS = 8
         "내전 1회 = 살인마 1판 + 생존자 4판. 그래서 절대 판수를 다르게 잡는다."
```

비율은 기록실 1:4, dbdzzk 1:2.7. **문제 인식이 동일하다.**
치즈스톰도 자동 티어에 최소 3경기, 포지션 통계에 최소 3경기 하한(`3a4c63e`)을 뒀다.

### 표본 미달 처리

```js
// dbdzzk tiers.js
/** 표본이 임계에 못 미치면 티어를 매기지 않는다 — 2판짜리 S가 신뢰를 깎는다. */
export function tierWithSample(norm, count, min) {
  return count >= min ? tierOf(norm) : '?';
}
```

치즈스톰 화면에도 `?` 미배정 티어가 있다. 기록실은 자격 미달자를 랭킹에서 뺀다.

## 2. 킬 점수 체계 — 4v4의 `3.5`

| | 치바데 | dbdzzk | 기록실 |
|---|---|---|---|
| 상수 | `VALID_4V4_STEPS = [1,2,3,3.5,4]` | `TEAM_OPTIONS = [0,1,2,3,3.5,4]` | 화면에 `3.5K` 표시 |
| 의미 | — | 3명 처치 + 개구 탈출 + 발전기 1개 | "따효니 개구 특별법" |
| 탈락자 수 | — | **내림** (3.5 → 3명) | — |

세 곳 모두 **개구(해치) 탈출을 0.5로 세는 로컬 룰**을 구현했다. 이건 커뮤니티 합의가 코드로 굳은 사례다.

## 3. 확정 승리 계산 — 매직 넘버 vs 콜드게임

```js
// dbdzzk magicNumber.js
const oppMax = oppScore + oppRemaining * MAX_KILLS;
const need = oppMax - myScore + 0.5;   // 점수 단위가 0.5라 0.5를 더한다
```

```ts
// 치바데 cold-warning.ts
const tMax = ts + tr * MAX_KILLS;
if (aMax < ts) return { status: "cold", name: adaName }   // 콜드게임 확정
```

**동일한 `현재점수 + 남은판수 × 4` 계산.** 차이는 출력이다.

| | dbdzzk | 치바데 |
|---|---|---|
| 상태 | `in-progress` / `clinch` | `none` / `warning` / `cold` / `gameover` |
| 경고 대상 | 내 팀 | 내 팀 **+ 상대팀 생존 조건** |
| 연계 조건 | 없음 | `survive_all` / `survive_min` / `survive_and_next_kill` |
| 노이즈 억제 | — | `myRem===1 && oppRem===1` 벼랑끝에서만 상대 경고 표시 |

치바데가 **경우의 수를 타입으로 다 갈라놨다.** dbdzzk가 이 기능을 다듬는다면 여기가 참고점이다.

## 4. 살인마 검색 — 초성 + 별명

```
dbdzzk   src/lib/chosung.js + killers.js  (별명 배열을 소스에 인라인)
         "'~구' 별명은 출처마다 갈리는 캐릭터가 있어(너스 순구/봉구, 처형자 삼각두/각구 등)"

치바데   data/characters.csv → generate-killer-catalog.mjs → killer-catalog.generated.json
         lib/fearless.ts 안에 KOREAN_INITIALS/JUNG/JONG 테이블 + hangulToSearchJamo()
         EXPECTED_KILLER_COUNT = 44 를 assert (CSV 깨지면 빌드 실패)
```

**같은 문제(한글 초성 검색 + 커뮤니티 별명), 같은 해법.** 살인마 수도 44로 일치한다(기록실 `/api/killers`도 44).

차이는 **초상화 조달**이다:

| | 방식 | 실패 시 |
|---|---|---|
| dbdzzk | DBD 위키 CDN 외부 URL | 이름 첫 글자, 실패 URL 재시도 안 함 |
| 치바데 | `/portraits/big/{id}.webp` **자체 호스팅** | — |

dbdzzk는 "저작권상 저장소에 번들하지 않는다"가 명시된 결정이다. 치바데는 그냥 넣었다.

## 5. 보안 경계 — 세 가지 다른 답

```
치바데   Firebase 익명 인증 + RTDB 규칙
         ownerUid === auth.uid 여야 쓰기, 방 ID는 48~128자리 hex,
         초대 토큰은 #room=... URL 프래그먼트, TTL 3시간을 규칙이 강제

dbdzzk   Firebase 익명 인증 + Firestore 규칙
         rooms/{code}: read 공개, create/update/delete는 ownerUid === auth.uid
         rounds 서브컬렉션은 부모 방 문서를 get()해서 소유자 확인

치즈스톰  치지직 OAuth + jose JWT → API 라우트 → Admin SDK
         Firestore 규칙: read=true, write=false (클라이언트 쓰기 전면 차단)
```

> [!important] dbdzzk가 치지직 로그인으로 가면 반드시 만날 벽
> ADR-0011 원문: *"Firestore 보안 규칙은 Firebase Auth 토큰만 검증할 수 있어, 커스텀 JWT로는 규칙 단에서 권한을 확인하는 방법이 없다."*
> dbdzzk는 지금 익명 인증이라 규칙으로 소유권을 검증할 수 있다. **치지직 OAuth를 붙이는 순간 이 검증이 무너지고, 쓰기를 전부 서버로 올려야 한다.** 치즈스톰이 이미 그 대가를 치렀다.

## 6. 티어를 자동으로 낼 것인가

| | 자동 | 수동 | 결론 |
|---|---|---|---|
| 기록실 | 레이팅(자동, 일일 스냅샷) | **원탁 티어표** — 작성자 `울프`가 킬러/생존자 점수를 직접 매김, 버전별 `announcedAt` | **분리** |
| 치즈스톰 | Elo + 승률 자동 티어 | 큐레이션 티어(권한자 드래그, 편집 로그) | **분리** (ADR-0005) |
| dbdzzk | `TIER_CUTS` S/A/B/C/D + 표본 미달 `?` | 없음 | 자동만 |

**두 프로젝트가 독립적으로 "자동과 수동을 섞지 말고 분리하라"에 도달했다.** ADR-0005의 문장이 이유를 가장 잘 말한다 — *"섞으면 둘 다 신뢰를 잃는다. 자동값을 수동으로 바꾸면 그게 승률인지 편애인지 알 수 없다."*

## 7. 재계산 가능한 지표를 굳히는 법

| | 장치 |
|---|---|
| 기록실 | **일일 스냅샷** (`takenAt` 23:00 UTC) + `previousTakenAt` 대비 `delta` + 티어표 **버전 선택** |
| 치즈스톰 | `stats/current` 사전집계 문서 + `unstable_cache` + 경기 변경 시 전체 재계산(80판 규모라 비용 무시) |
| dbdzzk | `freezeRoom` — 방을 얼려 라운드를 전적으로 승격 (v3, 미완) |

기록실이 제일 앞서 있다. 알고리즘을 두 번(08-14, 08-24) 고치고도 순위가 요동치지 않은 이유가 이 구조다.

## 8. dbdzzk가 지금 당장 훔칠 수 있는 것

1. **치바데 `cold-warning.ts`의 경고 상태 분해** — dbdzzk `magicNumber.js`는 계산은 같은데 출력이 단순하다. 연계 조건과 상대팀 경고를 타입으로 갈라두면 바로 쓸 수 있다.
2. **치바데 CSV → 빌드타임 카탈로그 생성 + count assert** — dbdzzk `killers.js`는 별명 배열이 소스에 인라인이라 추가할 때 코드를 건드린다.
3. **치즈스톰 `dedupe.ts`의 진영 스왑 대응** — 양 팀 합집합으로 비교. dbdzzk가 시청자 제보를 받으면 그대로 필요하다.
4. **기록실 `/api/*` 그대로 읽기** — 무인증 GET이다. 전적 화면을 직접 만들지 않고 붙일 수 있다.
5. **기록실 `takenAt` 스냅샷 패턴** — `freezeRoom`을 방 단위가 아니라 **집계 단위 일일 스냅샷**으로 재설계.

## 9. 반대로, dbdzzk가 이미 더 나은 것

- **포맷별 레이팅 풀 분리** — "4대4 1520과 5인 1480은 다른 눈금이다". 치즈스톰은 단일 풀이고, 기록실은 `ladders`로 분리해 dbdzzk와 같은 결론.
- **입력 검증을 시끄럽게** — `playedAt`이 비숫자면 `throw`. 치즈스톰은 정렬 타이브레이커까지만 갔다.
- **`compareMatches`를 `stats.js`와 공유** — 집계와 Elo가 **같은 재생 순서**를 쓰도록 export. 순서 의존 지표(streak 등)가 갈라지는 걸 구조로 막았다.
