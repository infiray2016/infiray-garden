# 치즈스톰 소스 분석

> `github.com/hongci9999/CheeseStorm-website` · PUBLIC · TypeScript · 라이선스 없음
> **297 커밋 · 기여자 1명 · 2026-06-10 ~ 2026-07-28 (49일)** · TS/TSX 158파일 20,918줄 · 테스트 29개

셋 중 **문서화가 압도적으로 두껍다.** `PROJECT.md`(프로젝트 기록서) + `CONTEXT.md` + `CLAUDE.md` + **ADR 22건** + `docs/study/` + `docs/agents/`.
`docs/superpowers/plans`·`specs` 디렉터리가 있다 — **dbdzzk와 같은 superpowers 워크플로**를 쓴다. `skills-lock.json`으로 외부 스킬(`mattpocock/skills`)을 해시 고정한다.

## 스택 (package.json 확정)

Next.js **16.2.9** · React 19.2.4 · Tailwind v4 + shadcn/ui + `@base-ui/react` · firebase 12 + **firebase-admin 14** · `jose`(JWT) · `zod` + `react-hook-form` · `@google/generative-ai` · Playwright(e2e) · Vitest.

## 읽기/쓰기 분리 — ADR-0011이 핵심

이 프로젝트에서 제일 중요한 결정이다. 원문 그대로:

> Firestore 보안 규칙은 Firebase Auth 토큰만 검증할 수 있어, **커스텀 JWT로는 규칙 단에서 권한을 확인하는 방법이 없다.** … 프론트엔드 `isStreamer` 체크는 UI 레이어에만 존재할 뿐 실질 보안이 아니었다.

```
rules_version = '2';
match /{document=**} {
  allow read:  if true;
  allow write: if false;   // 클라이언트 쓰기 완전 차단
}
```

```
브라우저 ──fetch──▶ Next API Route (jose JWT 검증) ──Admin SDK──▶ Firestore
브라우저 ──client SDK getDocs──▶ Firestore (읽기만)
```

**치지직 OAuth를 쓰기로 한 순간 Firebase Auth를 못 쓰게 됐고, 그래서 쓰기를 전부 서버로 올렸다.** dbdzzk가 익명 인증을 버리고 치지직 로그인으로 가면 똑같은 벽을 만난다.

### 읽기는 실시간이 아니다

소스 전체에 **`onSnapshot`이 0건**이다. `getDocs` 1회성 + 모듈 스코프 캐시(`getCachedStreamers` / `invalidateStreamersCache`) + 서버 컴포넌트 + `unstable_cache`.
(브라우저에서 `firestore.googleapis.com/…/Listen/channel`이 보이는 건 Firestore Web SDK가 1회성 쿼리도 WebChannel로 나르기 때문이지, 구독이 아니다.)

이유는 돈이다. `docs/firestore-reads-analysis.md`:

| 페이지 | 최적화 전 | 후 |
|---|---|---|
| 홈 1회 방문 | ~150 reads | **1 read** (`stats/current` 사전집계 문서 1건) |
| 1,000명 방문 | ~150,000 | ~1,000 |

Spark 무료 플랜 한도가 50,000 reads/일. "연 2~3주만 활성 → 월 과금은 낭비"라는 제약이 아키텍처를 결정했다.

## Elo — 12번 갈아엎은 기록

`src/lib/elo.ts` 커밋 이력이 그대로 실패 로그다.

```
22db549 Elo 순위표 탭 추가 — 상대 강도 + 개인 성과 반영
a02ad7d Elo 성과점수 절대값 정규화
9763d19 성과보너스 제거 → K-factor 조정 (Elo 합 보존)
f5f58de 성과점수에 경기 길이(dur) 반영
9cbc17f 표준 Elo 시스템으로 단순화
f2874c0 / 9bd3620 판수별 K-factor 조정 (초보자 진입 장벽)
e62a4d8 순수 표준 방식으로 복귀 + 계산 과정 추적 UI
7441ec7 등락폭 스케일링 — 기대승률 25/75%에서 ±K
fe0c437 등락폭 로지스틱 곡선 — 대등 ±20, 이변·압승에 포화
f3a3875 같은 날 경기 순서 타이브레이커 추가
c59afab 대회 경기를 Elo 집계에서 제외 (ADR-0022)
```

ADR-0020이 기각 사유를 남겼다 — 에이스/버스 개인 보정(M)은 **"승률 51% 68판 선수가 0승 6패 선수보다 낮아지는 역전"**을 실데이터 80경기/29명에서 만들어 폐기.

현재 코드:

```ts
const INITIAL_ELO = 1500;
const EQUAL_DELTA = 20;              // 기대승률 50%일 때 승자 +20
const MAX_DELTA  = 2 * EQUAL_DELTA;  // 점근 상한 40
const STEEPNESS  = 5 * Math.log(7);  // 30%→+35, 70%→+5 을 만족하는 기울기
function winnerGain(p){ return MAX_DELTA / (1 + Math.exp(STEEPNESS*(p-0.5))) }
```

> 내전은 밸런싱돼 기대승률이 30~70%에 몰리므로 그 구간을 가파르게, 바깥은 완만하게(포화) 만들어 이변에 크게·강팀 압승에 작게 반응시킨다.

> [!important] dbdzzk가 이미 만난 문제와 같다
> `f3a3875 같은 날 경기 순서 타이브레이커` — *"date는 시각 없는 자정값이라 같은 날 경기끼리 동점 → createdAt(입력 순)으로 확정. Elo는 경로 의존적이므로 이 타이브레이커가 없으면 최종 레이팅이 문서 ID 순에 좌우된다."*
> dbdzzk v3 커밋 `a2e82db elo 재생 결정성 강화 — playedAt 동시각은 roomCode로` 와 **같은 버그, 같은 해법**이다.

ADR-0022(대회 제외)의 논거도 그대로 옮길 만하다 — *"고정 로스터끼리의 반복 경기는 서로 독립이 아니라 '어느 팀이 센가'라는 관측 하나를 여러 번 세는 셈"*.

## 티어 이원화 — ADR-0005

> 객관(승률)과 주관(운영자 평가)은 둘 다 가치가 있으나 **섞으면 둘 다 신뢰를 잃는다** — 자동값을 수동으로 바꾸면 그게 승률인지 편애인지 알 수 없다.

그래서 오버라이드(핀) 대신 **완전 분리**. 자동 티어는 `calcPlayerStats` 불변식을 지키고, 큐레이션은 별도 문서(`curatedTiers`)에 저장.
ADR-0019는 여기에 **편집 히스토리 로그**까지 붙였다 — 공유 티어표를 누가 언제 바꿨는지.

## Gemini OCR — 생각보다 얇다

`src/app/api/parse-screenshot/route.ts`는 **96줄**이다.

```ts
const model = genAI.getGenerativeModel({ model: 'gemini-2.5-flash' });
```

무거운 파이프라인이 아니라 "모델에 이미지 던지고 구조화 응답 받기" 한 판이다. 대신 뒤를 받친다:
- `src/lib/ocr-corrections.ts` + `api/ocr-corrections` — **오인식 교정을 누적 학습**(선수·영웅 이름 매핑)
- `src/lib/dedupe.ts` — 중복 경기 탐지를 3단계로

```ts
type DuplicateLevel = 'none' | 'strong' | 'weak'
// strong: 날짜 + 10인 멤버셋 + dur 완전 일치 (POV 스왑 포함)
// weak  : 날짜 + 멤버셋 일치하나 신규 후보의 dur이 비어 있음
```

**양 팀 합집합으로 비교해서 진영(blue↔red) 스왑도 같은 경기로 잡는다.** 같은 내전을 서로 다른 스트리머 시점에서 두 번 올리는 상황을 정확히 겨냥한 설계.

## 스크림 영웅 티어 — Jenks 자연 분류

마지막 커밋(`64fa031`)이 제일 재미있다. `src/lib/scrim-stats.ts`:

> 밴픽률은 고르게 퍼지지 않고 계단식으로 뭉친다. 고정 구간(60%/50%/…)으로 자르면 표본이 적은 패치에서 티어가 통째로 비거나 한 티어에 다 몰린다.
> 이웃 낙차만 보고 자르는 방식은 실데이터에서 실패한다 — 경기 수가 적으면 관여율이 5%p 단위로 양자화돼 큰 낙차가 최상위에만 생긴다.
> 그래서 **Jenks 자연 분류(1차원 k-means, 정확해를 DP로)**로 군집 자체를 찾는다.

```ts
const TIER_GVF_TARGET = 0.97;  // 0.95면 "1티어 소수 + 2티어 전부", 0.99면 1인 티어가 줄줄이
const MAX_TIER_SEARCH = 8;     // 더 쪼개면 사람이 티어로 못 읽는다
const MIN_TIER_SPAN = 0.1;     // 관여율 폭이 이보다 좁으면 애초에 계단이 없다
// cost[k][i] = 앞 i개를 k군집으로 나눈 최소 SSE  →  O(k·n²)
```

**티어 개수를 사람이 정하지 않고 데이터가 정한다.** 상수마다 왜 그 값인지 실측 근거가 주석에 있다.
