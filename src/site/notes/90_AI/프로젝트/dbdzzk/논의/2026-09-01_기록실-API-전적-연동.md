## 왜 이 방향인가

v3는 **공개 전적을 직접 쌓으려다** 멈췄다. 그 길은 데이터가 0에서 시작하고, 오염 방지·승인 큐·스냅샷·재계산 결정성까지 전부 직접 풀어야 한다. 기록실은 그걸 이미 다 했고 62명·614경기를 갖고 있다.

**한 줄 요약: 우리가 못 가진 건 데이터고, 그 데이터는 무인증 GET으로 열려 있다.**

## 확인된 전제

### 1. 브라우저에서 직접 못 부른다 — 프록시가 필수다

```
$ curl -D- -H "Origin: https://dbdzzk.vercel.app" https://dbd.jetack.com/api/leaderboard
HTTP/2 200
cache-control: public, max-age=3
vary: Accept-Encoding
                          ← Access-Control-Allow-Origin 없음

$ curl -X OPTIONS ... /api/leaderboard
HTTP/2 405
allow: GET                ← 프리플라이트도 안 받는다
```

**치지직 API와 정확히 같은 상황이고, dbdzzk엔 이미 그 해법이 있다** — `api/chzzk.js`(Vercel 함수) + `vite.config.js`의 dev 프록시. 같은 모양을 하나 더 만들면 끝이다.

### 2. 조인 키가 이미 양쪽에 있다

```js
// dbdzzk src/lib/playerId.js
resolvePlayerId(p) → `chzzk:${p.chzzkChannelId}`  // 없으면 `local:${normalizeName(name)}`
```

```json
// 기록실 /api/players
{ "id": 18, "name": "HeavyRainy",
  "chzzkChannelId": "aef0c98592271de9ec4906eca2987e05", ... }
```

**`chzzkChannelId`가 그대로 조인 키다.** dbdzzk는 참가자 이름을 치지직 닉네임으로 보고 채널을 이미 조회해 저장하고 있다(`SetupPhase.vue`의 `fillProfile`). 즉 **연결에 필요한 작업이 이미 끝나 있다.**

동명이인·미등록은 `local:` 키로 떨어지고, 그건 그냥 배지가 안 붙는다.

### 3. 일일 스냅샷이라 캐시를 길게 잡아도 데이터가 안 낡는다

```json
"meta": { "takenAt": "2026-08-31T23:08:58Z", "previousTakenAt": "2026-08-30T23:00:00Z" }
```

레이팅은 **23:00 UTC(08:00 KST) 하루 한 번** 굳는다. 10분 캐시로도 최신성 손실이 사실상 없다.
상류가 `max-age=3`을 주지만 그건 진행 중 내전 화면용이고, 우리가 쓰는 건 굳은 값이다.

### 4. 응답 크기

| 엔드포인트 | 크기 | 우리 용도 |
|---|---:|---|
| `/api/tiers` | 0.9 KB | 원탁 티어표 (버전별 킬러/생존자 점수) |
| `/api/killers` | 24 KB | 살인마 픽률·밴율 |
| `/api/players` | 27 KB | **채널ID ↔ 선수ID 매핑** |
| `/api/leaderboard` | 87 KB | 전체 레이팅 |
| `/api/matches` | **340 KB** | 경기 전체 — **쓰지 않는다** |

`/api/matches`는 시즌이 갈수록 커진다. 우리에겐 필요 없다.

## 구조

```
브라우저 (dbdzzk)
   │  GET /api/jetack?resource=leaderboard
   ▼
Vercel 함수 api/jetack.js          ← 경로 화이트리스트 + CDN 캐시
   │  s-maxage=600, stale-while-revalidate=86400
   ▼
https://dbd.jetack.com/api/*       ← 무인증 GET, User-Agent: dbdzzk

개발환경: vite.config.js 프록시가 같은 경로(/api/jetack)를 흉내낸다
          → 클라이언트 파싱 코드는 하나로 유지 (api/chzzk.js와 같은 규약)
```

### `api/jetack.js` 초안

```js
// 열린 프록시가 되지 않도록 상류 경로를 고정 목록으로 못박는다 (api/chzzk.js와 같은 규칙)
const ALLOWED = {
  leaderboard: '/api/leaderboard',
  players:     '/api/players',
  killers:     '/api/killers',
  tiers:       '/api/tiers',
  version:     '/api/version',
};

export default async function handler(req, res) {
  if (req.method !== 'GET') { res.setHeader('Allow','GET'); return res.status(405).json({error:'method-not-allowed'}) }
  const path = ALLOWED[req.query?.resource];
  if (!path) return res.status(400).json({ error: 'invalid-resource' });

  try {
    const upstream = await fetch(`https://dbd.jetack.com${path}`, {
      headers: { 'User-Agent': 'dbdzzk (+https://dbdzzk.vercel.app)', Accept: 'application/json' },
      signal: AbortSignal.timeout(6000),
    });
    if (!upstream.ok) return res.status(502).json({ error: 'upstream-failed', status: upstream.status });
    // 레이팅은 하루 한 번 굳는다 — 10분 캐시로 최신성 손실이 없다
    res.setHeader('Cache-Control', 's-maxage=600, stale-while-revalidate=86400');
    return res.status(200).json(await upstream.json());
  } catch {
    return res.status(504).json({ error: 'upstream-unreachable' });
  }
}
```

`api/chzzk.js`와 **완전히 같은 뼈대**다. 메서드 제한 → 입력 검증 → 고정 상류 → 타임아웃 → CDN 캐시 → 실패 시 502/504.

## 무엇을 보여줄 것인가

### ① 팀편성 화면 — 참가자 카드에 레이팅 배지 (최우선)

이름을 넣으면 프로필 사진이 붙는 자리에 **레이팅과 원탁 티어 점수를 같이 붙인다.**

```
┌─────────────────────────────┐
│ (사진)  뱅                   │
│         종합 3,785  · 원탁 10 │
│         킬러 1,760 / 생존 2,025│
└─────────────────────────────┘
```

### ② 맞밸 배치의 입력을 바꾼다 ★ 이게 진짜 이득

지금 dbdzzk는 **실력치 1~5를 사람이 손으로 넣어야** 맞밸 배치와 에이스 선정이 돈다. 전원 입력해야 동작한다는 제약도 있다.

**기록실 레이팅이 들어오면 그 수기 입력이 사라진다.**

| | 현재 | 연동 후 |
|---|---|---|
| 입력 | 진행자가 8명 실력치 수기 | 자동 (채널ID 조인) |
| 근거 | 진행자 주관 | 614경기 누적 |
| 미입력 | 맞밸 배치 비활성 | 미등록자만 수기 보완 |
| 에이스 선정 | 실력치 차 최소 쌍 | 레이팅 차 최소 쌍 |

**진행 도구의 UX가 실제로 좋아지는 유일한 지점이다.** 전적 표시는 부가고, 이게 본체다.

### ③ 방 종료 후 요약 — "오늘 이후 예상"은 만들지 않는다

우리 방의 결과는 기록실에 안 들어간다(쓰기 API가 없다). 그러니 **오늘 내전을 반영한 레이팅은 계산하지 않는다.** 계산하면 기록실 값과 어긋나고, 어느 쪽이 맞는지 아무도 모르게 된다.
대신 "기록실에도 남기려면 →" 링크만 둔다.

### ④ 살인마 선택 화면 — 픽률·밴율 (선택)

`/api/killers`가 살인마별 픽률·밴율·평균 킬을 준다. 이미 있는 살인마 검색 UI에 한 줄 붙이면 된다. 우선순위는 낮다.

## 버리게 되는 것

이 방향을 택하면 **v3의 남은 12개 태스크 대부분이 사라진다.**

| dbdzzk 파일 | 운명 |
|---|---|
| `src/lib/elo.js` (98줄) | **불필요** — 기록실 레이팅을 쓴다 |
| `src/lib/tiers.js` (29줄) | **불필요** — 원탁 티어표를 쓴다 |
| `src/lib/stats.js` (225줄) | **불필요** — 집계를 안 한다 |
| `src/lib/playerId.js` | **핵심으로 승격** — 조인 키 생성기 |
| `src/lib/teamBalance.js` | 유지, 입력만 교체 |
| `src/lib/aceMatch.js` | 유지, 입력만 교체 |
| 승인 큐 · 오염 방지 · 스냅샷 | **애초에 만들 필요가 없다** |

> [!note] `DeathPicker` 결함도 성격이 바뀐다
> README 최상단의 그 결함은 "탈락자 기록이 오염돼 **집계**가 틀어진다"가 문제였다. 자체 집계를 하지 않으면 **공개 통계로 새는 경로가 사라진다.** 방 데이터 자체는 여전히 고쳐야 하지만, 등급이 "데이터 오염"에서 "진행 화면 버그"로 내려간다.

## 실패 모드 — 전부 조용히 죽어야 한다

dbdzzk README 규약: *"사진은 진행에 필수가 아니다"*. **전적도 마찬가지다.**

| 상황 | 처리 |
|---|---|
| 기록실 다운 / 타임아웃 | 배지 없이 진행. 오류 배너 금지 |
| 채널ID 없음 (`local:` 키) | 배지 없음. 수기 실력치로 폴백 |
| 기록실에 미등록된 사람 | 배지 없음 |
| 응답 스키마 변경 | 파싱 실패 시 그 사람만 배지 없음 — **전체가 죽지 않게** |
| API 자체가 사라짐 | 맞밸이 수기 실력치로 되돌아감 |

**단, Firestore 쓰기 규약(`try/catch` + `role="alert"`)은 여기 적용하지 않는다.** 전적은 읽기이고 장식이다. 실패를 사용자에게 알릴 이유가 없다.

## 리스크 — 솔직하게

1. **비공식 API다.** 문서화된 계약이 아니라 관측일 뿐이다. 예고 없이 바뀌거나 막힐 수 있다.
2. **막히면 끝이다.** 대체 데이터원이 없다. 그래서 맞밸은 수기 실력치 폴백을 반드시 유지해야 한다.
3. **남의 서버를 쓴다.** 캐시로 부하를 최소화하고(`s-maxage=600`), User-Agent에 dbdzzk를 밝히고, 화면에 출처를 표기한다 — "전적 데이터: [치지직 내전 기록실](https://dbd.jetack.com)".
4. **먼저 물어보는 게 맞다.** 기록실엔 게시판이 있다. 붙이기 전에 글 하나 남기는 게 예의고, 동시에 API 안정성 약속을 받을 유일한 방법이다.

> [!important] 첫 번째 할 일은 코드가 아니라 게시판 글이다
> "dbdzzk라는 진행 도구에서 팀 맞밸용으로 레이팅을 읽어가고 싶다. 캐시는 10분, 하루 요청 수는 N 이하"를 밝히고 양해를 구한다. 거절당하면 이 설계는 폐기하고 [[90_AI/프로젝트/dbdzzk/리서치/비교와-시사점\|1안(진행 UX 특화)]]로 간다.

- 기록실이 거절하면? → 1안으로. 이 문서는 폐기.
- `/api/version`을 저장해두고 SHA가 바뀌면 스키마 검증을 다시 돌릴 것인가? (있으면 좋지만 1차엔 과함)
- 5인 모드에도 레이팅을 쓸 것인가? 기록실 `ladders`에 `5p`가 따로 있다 — 포맷을 섞지 않는 dbdzzk 원칙과 맞는다. **4v4 먼저, 5인은 그다음.**
