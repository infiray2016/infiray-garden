# AI-Native SDLC 플레이북 (Anthropic) 정리

Anthropic 이 2026-08-21 에 공개한 "The AI-native SDLC playbook"(블로그 전문과 Claude Academy 14개 강좌)을 2026-10-16 03시에 원문으로 읽고 정리했다. 원문 사본은 [[90_AI/프로젝트/momo-english-academy/원자료/조사/2026-10-16_조사_AI-Native-SDLC-플레이북\|2026-10-16_조사_AI-Native-SDLC-플레이북]]. 우리 프로젝트가 이 플레이북을 어떻게 적용하는지는 [[90_AI/프로젝트/momo-english-academy/위키/방법론/AI-SDLC\|AI-SDLC]]에 있고, 어긋났던 곳의 대조표도 그 쪽에 있다. 이 쪽은 플레이북 자체의 요지라 모든 프로젝트에 같이 쓴다.

## 한 줄 요지

코드는 더 이상 병목이 아니다. 병목은 코드 둘레의 일(요구 정리 · 승인 · 검토 · 인수인계)이다. 플레이북은 그 일을 **단계마다 하나의 산출물(파일)을 커밋하는 것**으로 바꾼다. 단계는 그 커밋으로 끝나고, 그 커밋이 다음 단계를 연다. 커밋 사슬이 곧 감사 기록(누가 무엇을 원했고, 에이전트가 무엇을 만들었고, 누가 승인했는가)이다. 사람의 판단은 사라지지 않고 **게이트(승인 지점)**로 모인다. "루프는 계속 돌고, 사람의 판단은 그 위에 있다."

## 여섯 단계와 바뀌는 것

| 단계 | 전통 SDLC | AI-native SDLC | 끝에 커밋하는 산출물 |
|---|---|---|---|
| 1 Plan | 위원회가 요구를 모으고 워크숍 · 결재로 다듬어 손으로 적음 | 당사자가 Claude 와 브레인스토밍해 `intent.md`(사람이 읽고 기계가 실행할 수 있는 원시 명세)로 적음 | `intent.md` |
| 2 Design | 분석가가 명세를 쓰고 디자이너가 다시 읽음 | 요구사항과 설계를 에이전트와 한 세션에 압축. 조직 표준은 스킬로 걸고 git 에 버전 관리 | `spec.md` |
| 3 Build | 테스트와 코드를 손으로 쓰고 문서는 나중에 | 테스트와 코드를 AI 가 만들고, 조직 지식은 `CLAUDE.md` 와 스킬로 유지 | `plan.md`, 코드와 테스트 |
| 4 Test | 단계 경계의 QA 게이트 | 구현 내내 이어지는 평가(evals) | 테스트 결과 · 평가 결과 |
| 5 Deploy | 사람이 모든 줄을 검토, 거버넌스는 검토 주기에 | 에이전트 검토를 겹치고 사람 검토는 규제 · 핵심 코드에만. 거버넌스는 훅(승인 게이트)으로 행동 시점에 집행 | PR 과 검토 결과 |
| 6 Maintain | 사람이 운영을 지켜봄 | 에이전트가 운영을 지켜보고, 통제 띠를 벗어나면 진단해 새 `intent.md` 로 루프에 되돌림 | 사고 기록 · 새 `intent.md` |

승인된 `intent.md` 가 요구사항 · 설계 작업을 열고, 승인된 `spec.md` 가 plan mode 를 열고, 머지된 PR 이 파이프라인을 열고, 운영 지표 이탈이 다음 `intent.md` 를 쓴다. 처음에는 단계마다 사람이 손으로 띄우고, 끝 모습은 승인된 산출물이 다음 게이트를 저절로 여는 루프다.

## 열두 플레이

플레이마다 "바뀌는 것 · 시작하기(전제 · 기반) · 실행 순서 · 거버넌스 · 측정"을 적는다. 의존 순서가 있어 전제가 없는 플레이부터 시작한다.

### Plan — intent.md 로 잡기

- **단위:** 아이디어 하나, 티켓 하나, 운영 사고 하나가 `intent.md` 하나다. 제품 전체가 하나가 아니다. 당사자(기획자 · 운영자 · 아이의 부모 같은 비개발자)가 자기 말로 쓴다.
- **내용:** 문제(Problem) · 바라는 결과(Proposed outcome) · 영향받는 사용자와 시스템 · 제약 · 미결 질문. 해결책(화면 · 테이블)은 적지 않는다.
- **순서:** ① 당사자가 문제를 자기 말로 설명 ② 범위 · 사용자 · 제약 · 성공 기준이 구체해질 때까지 Claude 가 분석가처럼 질문 ③ 조직 템플릿(스킬로 만든다)대로 Claude 가 `intent.md` 를 씀 ④ 당사자가 오해를 고침 ⑤ 공유 저장소(`intent/` 폴더)에 커밋. 제품 소유자가 받아 들인다.
- **게이트:** 제품 소유자의 승인(머지 또는 검토 종결)이 Design 으로 보내는 결정이다. 커밋된 파일의 작성자 · 시각 · 수정 이력이 증거다.
- **측정:** 첫 대화에서 커밋까지 걸린 시간(주 단위 → 시간 단위), 승인되어 Design 으로 간 비율, 첫 `spec.md` 커밋 뒤에 `intent.md` 가 바뀐 횟수.

### Design — 요구사항과 설계를 한 세션에

- 승인된 `intent.md` 하나를 받아 Claude 가 요구사항 + 설계 명세를 쓴다. 브랜드 · 보안 · 규정 · UX 정책은 **스킬**로 걸어 쓰는 동안 적용한다. 지키지 못하는 정책은 **우려(flagged concern)**로 표시한다.
- 제품 소유자는 명세를 쓰지 않고 **검토**한다. 명세가 문제를 푸는지, intent 의 미결이 답해졋거나 넘겨졌는지 본다. 우려를 먼저 정책 소유자와 푼다.
- `spec.md` 를 `intent.md` 옆에 커밋한다. 두 파일이 "무엇을 원했고 무엇을 정했는가"의 짝이다. 제품 소유자가 Build 로 보낼지 정하고(위험이 크면 기술 리드와), 그 승인이 plan mode 플레이를 연다.
- 프롬프트 예: "첨부한 intent.md 를 읽고 우리 코드베이스에 넣을 요구사항 · 설계 명세를 써라. 스킬을 적용해 브랜드 · 보안 · UX 기준을 지켜라. spec.md 로 완전히 문서화하고, 특히 서로 충돌하는 정책을 만족시킬 수 없는 곳을 분명히 적어라."
- **측정:** `intent.md` 커밋과 `spec.md` 커밋 사이 시간, 첫 `plan.md` 커밋 뒤 `spec.md` 가 바뀐 횟수(빌드 시작 뒤 요구 재작업).

### Build — plan mode 가 기본 시작점

- 승인된 `spec.md` 를 들고 Claude Code 를 **plan mode** 로 시작한다. 코드를 바꾸지 못하는 상태에서 Claude 가 바뀌는 파일 · 작업 순서 · 증명하는 테스트를 적은 계획을 낸다. 엔지니어가 "무엇이 깨질 수 있나, 가장 위험한 단계는, 택하지 않은 다른 길은"을 캐묻고, **대화를 못 본 사람이 계획만 읽고 구현할 수 있을 때까지** 다듬는다.
- 승인된 계획을 `plan.md`(바뀌는 파일 · 순서 · 위험 · 증명)로 커밋한 뒤 구현한다. 구현이 계획을 벗어나면 같은 커밋에서 `plan.md` 를 고친다(훅으로 강제할 수 있다). 코드가 생기기 전에 설계 검토가 끝나는 것이 핵심이다.
- **auto mode:** 가드레일(다듬은 CLAUDE.md · 정책 스킬 · 위험 행동을 막는 훅 · Claude 가 돌릴 수 있는 테스트)이 익으면, 계획 승인 뒤 편집마다 묻지 않는 auto 가 일상 작업의 기본이 된다. 사람은 행동을 지켜보는 대신 긴 자율 세션 뒤의 산출물을 검토한다.
- **기존 시스템과 정본:** Jira · 요구 관리 도구 · Figma · 변경 위원회가 이미 기록을 들고 있으면, 산출물마다 **정본을 하나** 정한다(저장소가 정본 · 기존 도구가 정본 · 최소한 서로 링크). 둘이 공존해도 되지만 하나를 정본으로 선언한다.
- **CLAUDE.md:** 새 팀원이 첫날 알아야 할 것만(명령 · 규약 · 아키텍처 · Claude 가 자주 틀리는 것). `/init` 으로 만들고 한 쪽 안으로 줄여 git 에 둔다. **Claude 가 같은 실수를 두 번 하면 CLAUDE.md 에 적는다.** 측정은 CLAUDE.md 가 막았어야 할 실수를 되풀이한 횟수.
- **스킬 = 조직 지식의 실행형:** 일관되게 적용해야 할 지식(보안 표준 · API 규약 · 브랜드)을 `.claude/skills/<이름>/SKILL.md`(프런트매터는 언제 켜지는지, 본문은 무엇을 하는지)로. 정책 소유자가 바뀔 때 스킬을 바꾸고 서명한다. 스킬은 **권고 통제**라 반드시 지켜야 하는 것은 뒤에 결정적 장치(훅 · PR 검토 패스)를 둔다.
- **훅 = 빌드 시점 가드레일:** 보호된 경로 편집 차단, 편집 뒤 포매터 · 린터, 자격 증명이 diff 에 들어가는 것 차단. 빠르고 바뀐 파일에 한정. 사람 승인을 묻는 훅은 Deploy 의 게이트에 둔다(빌드 중 승인 프롬프트는 병렬 세션 전체를 사람에게 묶는다).
- **병렬 세션과 서브에이전트:** 세션은 worktree 로 나눠 파일이 겹치지 않게, 2~3개부터 시작해 검토가 따라가는 만큼만 늘린다. 반복 작업은 `.claude/agents/` 정의(이름 · 언제 쓰는지 · 쓸 도구)로 서브에이전트로 만들어 git 에 둔다. 예: 코드 단순화기, 앱을 돌려 보는 검증자(verifier, 고치지 않고 보고만), 코드베이스 조사자.

### Test — 스스로 확인하는 고리와 지속 평가

- **되먹임 고리:** Claude 가 자기 일을 확인할 길(테스트 · 빌드 · 스크린샷 비교)을 늘 준다. 한 명령(`make test`)으로 돌아가고 실패하면 0 이 아닌 값으로 끝나게. CLAUDE.md 의 Commands 에 건강한 출력 예를 적고, 목표를 수치로("test_status.py 전부 통과", "스크린샷이 목업과 같다"). 버그는 **실패하는 테스트를 먼저 쓰고 커밋한 뒤** 테스트를 고치지 못하게 하고 통과시킨다. UI 는 브라우저 · 스크린샷 도구로 구현 → 캡처 → 비교 → 수정을 두세 바퀴. "끝났다"에 검증을 포함하고 출력을 붙인다. 고치는 세션이 테스트 파일을 바꾸지 못하게 훅으로 막는다.
- 검증자 서브에이전트는 작업이 끝났다고 믿을 때 **새 컨텍스트**로 한 번 더 보는 포장이고, 되먹임 고리는 작업 내내 돈다.
- **지속 평가(evals):** 에이전트를 조종하는 설정(CLAUDE.md · 스킬 · 훅 · 모델 · 프롬프트)이 바뀔 때마다 실제 작업 20~50개를 평가로 돌려 같은 수준으로 일하는지 본다. CI 에서 비대화형(`claude -p`)으로, 일정과 `.claude/**` 변경 때. 통과율이 떨어지는 설정 변경은 머지 전에 검토. 운영 사고마다 평가를 하나 더한다. 모델이 좋아지면 가르지 못하는 사례를 빼고 새 사례를 넣는 살아 있는 묶음.

### Deploy — 양방향 검토와 승인 게이트

- **PR 검토 고리:** Claude 가 검토도 하고 검토 의견도 받는다. 모든 PR 에 같은 검토 패스(버그 · 보안 · spec.md 와 plan.md 와 설계 원칙 준수)를 돌리고 **심각도 순**으로 보고한다. 저장소 루트의 `REVIEW.md` 가 패스, **Important 의 뜻**(동작을 깨거나 데이터를 흘리거나 정책을 어기는 것. 스타일 · 이름은 사소), 사소 상한(예: 5개), 보고하지 않을 것(생성 파일 · CI 가 이미 검사하는 것)을 정한다. 지적은 PR 을 승인 · 차단하지 않고 사람(코드 소유자)이 의도와 위험만 본다. `@claude` 로 지적을 고치게 하고, 같은 실수가 두 번 걸리면 CLAUDE.md 에 넣는다. 달마다 지적을 평가해 검토자를 조율한다.
- **훅 = 승인 게이트:** 남겨야 하는 사람 승인(변경 관리 서명 · 배포 권한 · 보호 경로 편집)을 목록으로 적고 훅(허용 · 질문 · 차단 스크립트)으로 표현한다. 팀 훅은 `.claude/settings.json`, 양보 못 하는 훅은 관리 설정(개인이 끌 수 없음). 차단은 이유와 승인 경로를 함께 말한다.
- **규제 기업의 관리 설정 예:** 비밀 파일 읽기 · 임의 네트워크 차단, 안전한 안쪽 명령은 미리 허용, bypass 금지, 샌드박스 강제(도메인 허용 목록 · 자격 증명 경로 차단), 관리 훅 · MCP 서버만 허용, 승인된 플러그인 마켓만, 최소 버전. 복사 말고 데이터 등급에 맞게 조정.
- **CI/CD 통합:** 파이프라인 안에서 비대화형으로 판단이 필요한 단계(깨진 빌드 분류 · 불안정 테스트 요약 · 변경 기록 초안)부터, 쓰기 단계는 기존 게이트 뒤에서 PR 로만(main 직접 푸시 불가). 샌드박스와 짧은 토큰. 배포 · 상태 · 롤백을 MCP 도구로 노출해 환경별 허용 목록으로. 개발은 자유, 운영은 릴리스 매니저가 승인하고 훅이 집행. **롤백은 가장 많이 연습된 한 줄 명령**이어야 한다(Maintain 의 루프가 부른다).

### Maintain — 루프 닫기

- 결정적 스크립트가 운영 지표(CI 실패율 · 배포 뒤 5xx · PR 주기 시간)의 통제 띠(이동 평균 · 표준편차, Western Electric 규칙)를 감시한다. 1σ 는 기록만, 2σ 는 Claude 가 읽기 전용으로 진단, 3σ 는 PR 을 열거나 미리 승인된 런북(롤백)만 실행. 티어는 버전 관리된 설정(`bands.yaml`). 탐지는 모델 없이 결정적으로.
- Claude 는 진단을 Plan 단계 형식의 `intent.md`(이상 · 증거 · 바라는 결과 · 영향 시스템 · 미결)로 쓰고, 그 뒤는 보통 변경과 같은 길을 간다. 서비스 소유자가 "지금 고침 · 일정 · 기각"을 분류하고, 기각은 띠를 조율한다. 고친 사고마다 평가를 더한다.
- **정기 코드베이스 스캔:** 보안 스캔은 시점 진술이라 코드와 모델이 함께 낡는다. 일정으로 돌리고 결과를 다른 변경과 같은 게이트로 보낸다. 한 PR 에 드는 수정은 PR 로, 더 큰 것은 `intent.md` 로. 기각에는 이유를 적어 같은 결과가 다음 번에 새로 뜨지 않게.
- **채널의 Claude(Claude Tag):** Slack 같은 채널에 Claude 가 자기 신원으로 들어가 사고의 첫 대응자가 되고, 채널 기록이 감사 기록이 된다. 작은 수정은 PR 로, 큰 것은 `intent.md` 로.

## 우리에게 바로 닿는 규칙 (요약)

| 규칙                           | 뜻                                                                       |
| ---------------------------- | ----------------------------------------------------------------------- |
| 변경 단위마다 intent 하나            | 제품 intent 하나로 모든 변경을 받지 않는다. 검토 루프 중에 요청자가 낸 새 요구도 intent 로 먼저 쓰고 승인받는다 |
| intent 와 spec 은 짝            | spec 은 승인된 intent 하나에 대한 델타(정본의 어느 절이 바뀌는가)이고, 둘을 함께 커밋한다               |
| 단계의 끝은 커밋                    | 승인 지점마다 커밋이 있어야 감사 기록이 된다                                               |
| 우려는 표시하고 소유자가 푼다             | 검토자의 지적은 '우려'로 모아 제품 소유자(요청자)가 승인 때 본다. 세부는 위임받은 사람이 정하되 승인 때 한 번에 보인다  |
| plan 은 plan mode 로, 코드 전에    | 바뀌는 파일 · 순서 · 위험 · 증명. 대화를 못 본 사람도 구현할 수 있게                             |
| CLAUDE.md 는 한 쪽, 두 번 틀리면 적는다 | 요지와 참조만. 상세는 스킬 · 훅 · 위키                                                |
| 스킬은 권고, 훅은 강제                | 반드시 지킬 것은 훅으로                                                           |
| 검토는 심각도와 근거, 사소 상한           | REVIEW.md 에 패스 · Important 의 뜻 · 사소 상한 · 보고하지 않을 것                      |
| 서브에이전트는 반복 작업에, 2~3개         | 모델 · 추론은 용도별([[90_AI/프로젝트/momo-english-academy/위키/결정/결정-목록\|결정-목록]] 10-16 02:00)                                     |
