# 개발 흐름

> pickzzk 의 작업 패턴 / R 시리즈 / commit 컨벤션 / 검증 / 워크플로.

## R 시리즈

> "R<N>" = pickzzk 의 큰 작업 단위. 1 R 안에 여러 C<N> commit.

각 R 시리즈 = 큰 주제 (e.g. v2 schema migration / 멀티 경매 / 활성 홈 폴리싱 등). 한 R 안의 C 들은 small focused commits.

### R 시리즈 누적

| R | 주제 | 박힌 기간 | commit 수 | 박힌 commit |
|---|---|---|---|---|
| R20 | v2 schema migration + 멀티 경매 | 2026-05-08 ~ 2026-05-12 | 18 (C1~C14d) | …`a540398` |
| R21 | 활성 홈 폴리싱 | 2026-05-13 ~ 2026-05-14 | 5+ (C1~C5+) | …진행 |

자세히는 `CHANGELOG.md` (각 R 시리즈 박힌 기록).

## C<N> commit 컨벤션

```
<type>(<scope>): R<N> C<N> — <한 줄 요약>

본문 (3~5 문단):
- 무엇을 박았나
- 왜 박았나 (user 박힌 결정 / 자료 출처)
- 검증 결과 (lint / regression / build / Playwright)
- Deferred (다음 commit 으로 박힐 거)

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
```

예 (R21 C2):
```
feat(active-home): R21 C2 — TimelineHero 고도화 (D-day + stage 별 메인 CTA)

활성 홈 hero 카드 강화. 시청자가 '다음 단계까지 얼마 남았나' + ...

1 decision (한 번에 하나, feedback_decision_one_at_a_time.md):
- Q1=C: D-day + stage CTA 버튼 (메인 키 액션) 둘 다.

- src/composables/useTournamentTimeline.js:
  - 신규 dDayLabel(at, now) pure helper.
  - ...

Tests +9 (totals 345 pass):
- dDayLabel: 같은 날 / 미래 / 과거 / null / Date 인스턴스 / default now (6 cases)
- ...

Verify: lint 0 errors / regression 345 pass / build 2.81s / Playwright 1440·375
console 0/0. mock/scrim/final stage 3 viewport 확인.

Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
```

### type 컨벤션

- `feat()` — 신규 기능 / 화면
- `fix()` — 버그 fix
- `chore()` — 폴리싱 / docs / 빌드 / 리팩토링
- `test()` — 테스트 추가
- `refactor()` — 구조 변경 (행위 동일)
- `docs()` — 문서만

### scope 컨벤션

- `active-home` — 활성 홈
- `auction-multi` — 멀티 경매
- `mock` — 모의 시뮬
- `archive` — 아카이브
- `scrim-day` / `scrim-game` — 스크림
- `admin-setup` — 운영자 셋업
- `streamers-db` — 스트리머 DB
- `infra` — 빌드 / 인프라
- ...

## 워크플로 (R11 — 7 단계)

1. **Skill 정독** — 작업 영역 [[90_AI/claude/개념/스킬\|스킬]] 먼저 읽음
2. **AS-IS 확인** — 현재 코드 / Playwright 시각 확인 (R4)
3. **설계 / Plan** — `.claude/R<N>_C<N>_PLAN.md` 박음 (R12)
4. **결정 받기** — 한 번에 하나 (R13, `feedback_decision_one_at_a_time.md`)
5. **구현** — 작은 commit 단위
6. **검증** — lint + regression + build + Playwright (R1)
7. **R15 docs 동기** — CHANGELOG / RETRO / TODOS 갱신

### Step -1. /checkpoint (R14)

큰 작업 진입 전 → `/checkpoint` 즉시. 터미널 종료 / context 손실 대비.

## 결정 박는 패턴

> [!info] 한 번에 하나

예 (R21 C2): "D-day 박는 위치" 한 결정만 4 옵션 (A/B/C/D). 답 박힌 후 다음 결정.

## 검증 룰

### Code 변경 후

```bash
bun run verify            # lint + regression + build 한 번에
```

### UI 변경 후

Playwright MCP 로 3 viewport:
- 375 (mobile)
- 768 (tablet)
- 1440 (desktop)

console error/warn 0 + 시각 확인.

### 검증 실패 시

- 코드 박지 마 / 검증 안 박는 commit X
- silent fail X — `console.warn` 박아 가시화 (5 trap pattern)

## docs 동기 (R15)

R<N> commit 박힐 때 반드시:

| docs | 갱신 |
|---|---|
| `CHANGELOG.md` | 박힌 내용 / 결정 / verify 결과 |
| `README.md` | 사용자 가시 변경 있으면 |
| `RETRO.md` | 큰 R 시리즈 끝나면 회고 |
| `TODOS.md` | 다음 R 시리즈 후보 / R 진행 누적 |

> [!warning] R15 누락 = 즉시 정정
> commit 박은 후 docs 빠지면 user 가 "문서는 왜 빠졌어 ?" 정정. R15 의 출처.

## R 시리즈 끝 = retrospective

`RETRO.md` 에 회고 박음:
- 잘 된 점 (✅)
- 막힌 점 (⚠)
- 다음에 다르게 할 것 (🎯)

자료 = `feedback_*.md` 메모리 / 잡힌 정정 사례.

## verify 박을 때 순서

1. 코드 박음
2. `bun run lint` (Prettier check) — 에러 시 `bun x prettier --write <file>` 으로 자동 정정
3. `bun run regression` (vitest)
4. `bun run build` (production)
5. Playwright 3 viewport (UI 변경 시)
6. console 0/0 확인

다 통과 = R15 docs 동기 → commit + push.

## 헷갈리는 점

> [!warning] 푸시 = main 차단됨
> Claude 가 main 에 push 시도 = system 이 차단. `git push origin main` 은 user 가 명시 승인 (또는 settings.json 에 룰 추가).

> [!warning] `--no-verify` 박지 마
> Pre-commit hook fail = 코드 fix. hook skip 금지.

> [!warning] amend 박지 마
> 새 commit 박음. amend 는 user 명시 시만.

> [!warning] sub-agent 결과 verify
> [[90_AI/claude/개념/서브에이전트\|서브에이전트]] 결과 = text 만. 실 변경은 메인 에이전트가 git diff / build 검증.
