# 제보 큐 (운영자)

> 시청자 제보 (`scrimSubmissions/`) 승인 / 반려 / 정정. **2 명 합의 / 자가 합의 방지** 룰 박힘.

## URL / 뷰

- URL: `/admin/submissions`
- View: `src/views/admin/SubmissionsView.vue` (또는 admin views/)
- 권한: admin only

## 표시 / 박는 것

```
헤더: 제보 큐 (대기 중 N 건)
├── 필터 (대기 / 승인 / 반려 / 전체)
├── submission list
│   ├── 각 row: 제보자 / kind / date / teams / score / 미리보기
│   └── row 클릭 → 검토 drawer / modal
└── 일괄 작업 (선택 후 승인 / 반려)
```

## 검토 drawer

각 submission 진입 시:
- 원본 이미지 (썸네일 + 확대)
- Claude Vision parse 결과 (chip 형식 — 정정 가능)
- 정정 + 정정 사유 메모
- 동일 제보 의심 check (`useDuplicateCheck`)
- 승인 / 반려 / 보류 버튼

## 도메인 룰 (`screen-admin-submissions` 스킬)

> **2 명 합의 / 자가 합의 방지**

- 1 제보 = 운영자 2 명 박힘 필요 (승인 reach 2)
- 같은 운영자가 박은 제보는 본인 승인 X (자가 합의 방지)
- 합의 reach 시 `scrimSubmissions` → `scrimDays/{date}/games/` promote

자세히는 [[90_AI/claude/개념/스킬\|스킬]] / `screen-admin-submissions/SKILL.md`.

## 데이터 source / 흐름

```
시청자 제보
  → POST /api/scrim-submit
  → scrimSubmissions/{id} 박힘 (status='pending')
     │
운영자 A 승인 → approvals: [uidA]
     │
운영자 B 승인 → approvals: [uidA, uidB] → status='approved'
     │
promote → scrimDays/{date}/games/ 박힘
     ↓
scrimSubmissions/{id} → archive 또는 history 박힘
```

## composable

- `useSubmissionsQueue(filterRef)` — 큐 onSnapshot + filter
- `useSubmissionReview(submissionId)` — 1 submission editor
- `useDuplicateCheck()` — 동일 제보 의심 check
- `useAdminGate()`

## API

`POST /api/scrim-admin`:
```json
{
  "secret": "$SCRIM_ADMIN_SECRET",
  "action": "approveSubmission" | "rejectSubmission" | "promoteSubmission",
  "submissionId": "...",
  "approverUid": "...",
  "corrections": { ... }  // 정정 박을 경우
}
```

자세히는 `docs/firebase-rules.md`.

## scrimSubmissions schema

```js
scrimSubmissions/{id}: {
  tournamentId: "hojong-cup-5",
  kind: "inhouse" | "official-scrim" | "unofficial-scrim" | "final",
  date: "YYYY-MM-DD",
  teams: { teamA, teamB },
  score: { ... },
  picks: [...],
  bans: [...],
  kda: [...],
  mvp: "...",
  submittedBy: "uid | anonymous",
  submittedAt: serverTimestamp,
  imageUrl: "...",  // storage url (원본 이미지)
  status: "pending" | "approved" | "rejected" | "promoted",
  approvals: [uid, uid],  // 운영자 승인 박힘
  corrections: { ... },  // 정정 박힘 (마지막 운영자)
  promotedGameId: "...",  // promote 후 game id (audit)
}
```

자세히는 [[90_AI/프로젝트/pickzzk/위키/데이터-모델\|데이터-모델]].

## 동일 제보 의심

> `useDuplicateCheck`:
> - 같은 date / kind / teams (case-insensitive) 가까운 시간 (1 시간 내) 제보 있나
> - 같은 제보자 (`submittedBy`) 가 5 분 안에 박은 거 = 자동 의심

## audit / history

- 승인 / 반려 / 정정 모두 audit log 박힘
- promote 후에도 `promotedGameId` 박혀 추적 가능
- 운영자 정정 시 원본 vs 정정 diff 보존

## 박힌 R 시리즈

- (R20 이전) legacy scrim submissions UI 포팅
- Codex 리뷰 #6 — winner 라벨 hard-code (`AdminSubmissionsView.vue:221`) 잔여 (`CODEX_REVIEW.md` Tier A)

## 활성 홈 표시

> [!info] 제보 큐 status = 활성 홈 / sidebar 카운트 표시 후보
> `pending` count → 운영자 sidebar 의 "제보 큐" 옆 배지. R22+ 후속.

## 헷갈리는 점

> [!warning] 자가 합의 방지 = 필수
> 1 운영자가 모든 제보를 박을 수 없음. 다른 운영자 승인 필수.

> [!warning] 정정 + 승인은 별 action
> 정정 박은 후 승인 박아야 함. 정정 자체 = 승인 X.

> [!warning] promote = scrimDays/ 박힘 + scrimSubmissions audit
> promote 후 scrimSubmissions doc 은 history 박힌 채 보존. 지우지 X.

> [!warning] anonymous 제보도 받음
> submittedBy 가 `'anonymous'` 가능. 단 duplicate check + 정정 시 더 신중.
