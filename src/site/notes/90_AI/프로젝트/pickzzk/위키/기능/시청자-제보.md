# 시청자 제보 (server-side 자동 승격, R22 진입 후)

> 시청자가 게임 결과 OCR 제보 → Vercel serverless 함수 (`/api/scrim-submit`) 가 admin SDK 로 Firestore submissions/ 박음 + 같은 운영일 다른 제보들과 합의 판정 동기 처리 → **시청자 두 명 이상 합의 시 즉시 정식 결과 (scrimDays/{date}/games/{id}) 로 자동 승격**. 운영자가 admin 큐 페이지 안 켜둬도 자동 동작.

## R22 진입 후 흐름 (2026-05-18 박힘)

이전엔 viewer client 가 직접 Firestore 의 submissions/ 에 박고, 운영자가 admin 큐 페이지를 켜둔 상태에서만 client watcher 가 합의 판정 + promote. 운영자가 페이지 닫으면 영원히 pending — 활성 시즌에 운영자가 24시간 켜둘 보장 X 라서 R22 에서 server-side 로 옮김.

### 전체 흐름 (R22 후)

```
1. 시청자가 [[../페이지/시청자-제보]] 진입 (또는 GameInput viewer 모드)
   ↓
2. 결과창 / 전적 이미지 업로드
   ↓
3. Claude Vision OCR ([[OCR]]) — server side (`/api/scrim-parse`)
   ↓
4. 시청자가 mapping 확인 / 정정 (player ↔ streamer / champion 등)
   ↓
5. POST /api/scrim-submit
   { gameData, submitter:{role, clientId}, operationalDate, matchedCluster }
   ↓
6. server (api/_lib/scrim-submit-handler.js) 가 admin SDK 로 박음
   - submissions/{id} create (status='pending')
   - 동기 합의 판정 (tryConsensusPromotion)
     ├── 같은 운영일 pending 들 조회 (composite index 사용)
     ├── gamesMatch 로 같은 경기 매칭 (KDA ±1 / gold ±2% / dmg ±3% / duration ±3s / 10 슬롯)
     ├── 고유 clientId ≥ 2 면 → 합의 성립
     │   - 자가 합의 방지: 같은 clientId 두 번 박아도 1표
     │   - 익명 총합 최대 1표
     └── 합의 성립 시 Firestore batch atomic:
         ├── scrimDays/{date}/games/{newId} create (source='auto-consensus')
         └── 매칭 submissions 모두 delete
   ↓
7. response: { ok, submissionId, consensus:{ promoted, gameId?, matchCount, uniqueClients } }
   ↓
8. 활성 홈 / 스크림 DAY 자동 표시 (onSnapshot)
```

핵심: client 측 setupAutoPromotion 코드는 R22 C7 (`14e2a3a`) 에서 제거됨. server 가 single source of truth.

## 도메인 룰 (`screen-admin-submissions` 스킬 정합)

### 시청자 두 명 합의 = 자동 승격

> 같은 경기 제보를 **서로 다른 두 시청자** (다른 clientId) 가 박으면 즉시 정식 결과로 승격. 한 명만 박은 거 = pending 유지.

이유:
- 시청자 제보 = 잘못된 데이터 가능 (OCR 오인 / 의도적 / 실수)
- 한 명만 박음 = 자의적 위험
- 서로 다른 사람 두 명 합의 = 신뢰성 확보
- 운영자 직접 승인 불필요 — 자동

### 자가 합의 방지

> 같은 clientId 가 같은 경기를 여러 번 박아도 한 표만 인정. 익명 (clientId 없음) 은 총합 최대 한 표.

이유:
- 한 명이 두 시크릿 창에서 두 번 박는 식의 self-conspiracy 방지
- 익명 제보는 누가 박는지 모르니 보수적으로 총합 1표만

server 안 11 LOC 짜리 단순 로직 (`Set` + `filter`). 회귀 가드 통합 테스트는 아직 미박음 — [[../할일/2026-05-18 개선사항\|../할일/2026-05-18 개선사항]] entry.

### gamesMatch tolerance (legacy verbatim)

같은 경기인지 판정하는 룰 — legacy DraftPick 의 R22 C2 포팅 시점에 verbatim 어댑트. R22 C8 (`24d7080`) 에서 회귀 가드 32 케이스 박음 (`tests/unit/games-match.test.js`).

비교 축:
- 팀 (teamAId / teamBId) + 승자 (winnerTeamId) — 정확 일치
- duration — ±3 초 허용
- 10 명 player (A/B × Top/Jungle/Mid/ADC/Support):
  - champion / playerName — 정확 일치
  - KDA (kills / deaths / assists 각각) — ±1 허용 (OCR 오차)
  - gold — ±2% 허용 (max 기준)
  - totalDamage — ±3% 허용 (max 기준)

한 축이라도 어긋나면 합의 X. 박힌 reasons 배열로 어디서 어긋났는지 추적 가능.

### admin 큐 페이지 = read-only + 수동 승인/반려만

R22 후 admin 큐의 역할:
- pending 제보 목록 read-only 표시
- 자동 승격 안 된 단일 제보 (한 명만 박은 거) 수동 승인 / 반려
- kind 정정 (default = stage 보고 추정, 운영자가 정정)
- 강제 승격 액션 — 박힌 라벨 `admin-consensus` (vs server 자동 = `auto-consensus`)

이전엔 admin 큐 페이지의 client watcher 가 자동 promote 도 담당했는데 R22 C7 에서 그 코드 제거. 페이지 mount 의존성 사라짐.

> [!warning] anonymous 제보도 받음
> 시청자가 로그인 안 해도 박음 OK. 단 익명은 총합 한 표만 인정 — 익명 두 명이 같은 경기 박아도 합의 X.

## 데이터 source

### `submissions/{id}` (Firestore — R22 후)

```js
{
  gameData: {
    teamAId: "...",
    teamBId: "...",
    winnerTeamId: "...",
    durationSeconds: 1800,
    players: [10명 — teamSlot/role/teamId/champion/playerName/kills/deaths/assists/gold/totalDamage]
  },
  submitter: {
    role: "viewer",            // 또는 "admin" (운영자 직접)
    clientId: "...",           // 자가 합의 방지 키. 익명이면 undefined
    displayName: "..."         // 옵션
  },
  status: "pending",            // R22 후로는 합의 성립 시 server batch 가 delete — 'approved' 같은 중간 status X
  matchedCluster: "...",        // OCR mapping 단계의 cluster key
  operationalDate: "YYYY-MM-DD",
  createdAt: serverTimestamp
}
```

차이 (이전 schema 와):
- 컬렉션 명 = `submissions/` (이전엔 RTDB `scrimSubmissions/` — legacy DraftPick. pickzzk v2 는 Firestore 메인)
- `approvals: [uid, ...]` 같은 운영자 승인 트래킹 필드 → R22 후로는 합의 시 server batch 가 도큐 자체 삭제 → 운영자 승인 흐름 자체 변형
- `imageUrl` → 현재 pickzzk 는 viewer-edited only (mapping 확정된 gameData 만 server 로 보냄). 원본 이미지 별도 보관 X

### `scrimDays/{date}/games/{gameId}` (합의 후 박힌 결과)

```js
{
  ...gameData,              // submissions/{id}.gameData 복사
  seriesId: null,
  submitter: { role: "auto-consensus" },  // server 자동 또는 "admin-consensus" (강제) / "admin-direct" (admin 직접 입력)
  consensusFrom: [submissionId, ...],     // 매칭됐던 submissions ID 들 (audit)
  consensusCount: 2,                       // 매칭 수
  consensusUniqueClients: 2,               // 고유 clientId 수
  createdAt: serverTimestamp,
  startedAt: serverTimestamp
}
```

자세히는 [[90_AI/프로젝트/pickzzk/위키/데이터-모델\|데이터-모델]].

### Firestore rules + indexes (R22 후 정합)

- `submissions/` create / update / delete = admin only (R22 C5, `6587bd3`) — viewer 는 server endpoint 만
- read = admin (큐 표시용) + 도큐 단건 read 는 public
- composite index `submissions (status ASC, operationalDate ASC)` — server consensus query 필수 (R22 C6, `14e2a3a`)

## API

### `POST /api/scrim-submit` (viewer + server 자동 합의)

body: `{ gameData, submitter, matchedCluster, operationalDate }`

response (합의 미달):
```json
{
  "ok": true,
  "submissionId": "abc...",
  "consensus": { "promoted": false, "matchCount": 1, "uniqueClients": 1 }
}
```

response (합의 성립 — 두 번째 다른 clientId 박을 때):
```json
{
  "ok": true,
  "submissionId": "xyz...",
  "consensus": { "promoted": true, "gameId": "newGameId", "matchCount": 2, "uniqueClients": 2 }
}
```

검증 결과 (2026-05-18 production dry-run): 1차 `promoted: false`, 2차 (다른 clientId) `promoted: true + gameId 발급` 정합.

### `POST /api/scrim-admin` — 운영자 액션

- `approveSubmission` — 단일 제보 강제 승격 (admin-consensus 라벨)
- `rejectSubmission` — 반려 (도큐 status 변경 또는 삭제)
- `correctSubmission` — gameData 정정 + audit log

자세히는 `api/scrim-admin.js` (legacy 포팅, 코드 확인).

## composable

- `useScrimSubmit(...)` — viewer 측 fetch `/api/scrim-submit` 래퍼. submitter / clientId / operationalDate / matchedCluster 자동 박음
- `useSubmissionsQueue(filterRef)` — admin 큐 onSnapshot + filter. R22 C7 후로는 read-only — autoPromotion 코드 제거됨
- `useSubmissionReview(submissionId)` — 단일 submission editor (수동 승인 / 반려 / 정정)
- `useDuplicateCheck()` — 동일 제보 의심 감지
- `useAdminGate()` — admin 권한 체크

## audit / history

- `submissions/{id}` 자체는 합의 시 server batch 가 삭제 — audit 는 `scrimDays/{date}/games/{gameId}` 의 `consensusFrom[]` 으로 추적
- 강제 승격 (admin) / 자동 승격 (server) 구분 = `submitter.role` 라벨 (admin-consensus / auto-consensus)
- 운영자 정정은 `scrimDays/.../games/{gameId}` 도큐의 update 로 박힘. 변경 audit log 는 별도 TBD

## 동일 제보 의심 (`useDuplicateCheck`)

자동 check:
- 같은 operationalDate / matchedCluster
- 가까운 시간 (1시간 내)
- 같은 clientId 가 5분 내 박은 거

→ 의심 시 운영자에게 warning + 정정 / merge 옵션.

R22 후로는 server 의 자가 합의 방지가 1차 가드, useDuplicateCheck 는 운영자 검토 단계의 보조.

## viewerRatings 와 차이

> viewerRatings = 시청자 ★ 평가 (per-fingerprint dedupe). 시청자 제보와 다른 영역.

| 영역 | 시청자 제보 | viewerRatings |
|---|---|---|
| 무엇 | 게임 결과 데이터 (OCR + 매핑) | 시청자 평가 (★) |
| 합의 방식 | 시청자 두 명 자동 (server consensus, R22) | per-fingerprint dedupe |
| 현재 상태 | active | deferred (재오픈 product 결정 필요, Tier 2) |

자세히는 [[90_AI/프로젝트/pickzzk/위키/기능/스크림-집계\|스크림-집계]] 의 viewerRatings 섹션.

## 헷갈리는 점

> [!warning] 합의 = 시청자 두 명 (운영자 X)
> R22 전엔 "운영자 2명 승인" 이었는데 R22 후로는 **시청자 두 명 합의 자동 승격**. admin 큐는 read-only + 수동 승인은 단일 제보 보조용.

> [!warning] 자가 합의 방지 = clientId 기준
> 같은 clientId 두 번 박아도 1표. 익명 (clientId 없음) 총합 1표. 회귀 가드 통합 테스트는 아직 미박음 — 활성 시즌 직전 박을 entry [[../할일/2026-05-18 개선사항\|../할일/2026-05-18 개선사항]].

> [!warning] 합의 안 된 단일 제보 stale 누적 가능
> server batch 는 합의된 것만 삭제. 한 명만 박은 거는 운영일 + 24h 지나도 영원히 pending. 자동 만료 cron 또는 TTL 룰 박을 entry [[../할일/2026-05-18 개선사항\|../할일/2026-05-18 개선사항]].

> [!warning] kind 는 시청자가 박지 않음
> 시청자 제보 시 kind 는 stage 보고 자동 추정 (pre-open/mock → inhouse / scrim → official-scrim default / final → final). 운영자가 큐에서 정정.

> [!warning] viewer-edited only (mapping 확정 후 server 로)
> pickzzk 의 viewer 는 GameInput 에서 OCR + mapping + 교정 완료한 후 확정된 gameData 만 server 로 보냄. server-side OCR/normalize 불필요 (legacy 와 차이).
