# 2026-06-11 인식 품질 한 바퀴 — 게임결과 OCR 업스케일 · 선수 매칭/수치 검산 · 자가개선 재학습 인프라 · 밴 ROI 로딩 화면 대응

## 무엇

게임 결과·픽밴 자동 인식의 정확도를 끝까지 끌어올린 큰 작업 묶음. 시작은 "6월 10일 올린 경기 인식이 너무 떨어진다"는 한 줄이었는데, 파고들면서 게임결과 OCR → 선수 매칭 → 수치 검산 → 밴 분류기 학습 인프라 → 밴 ROI 검출까지 인식 파이프라인 전체를 한 바퀴 정리했다.

## 왜

시청자가 스크린샷 한 장으로 경기 결과를 제보하는 흐름이 픽지직의 핵심 데이터 입구다. 여기 정확도가 낮으면 시청자가 10행을 일일이 손보고, 합의 승격도 안 되고, 지표도 노이즈가 낀다. "자동 운영" 비전의 신뢰가 여기서 갈린다.

## 어떻게

### 1차 — 게임결과 OCR: 작은 이미지 업스케일이 진짜 원인

처음엔 "챔프를 이미지로도 인식하자"는 요청으로 시작했는데, production 데이터를 직접 조회해 보니 챔프 이미지 분류기(사실 밴 화면용 모델을 재사용 중이던 것)가 30명 중 거의 다 틀리고 있었고, 맞은 텍스트 OCR까지 "검토"로 끌어내리고 있었다. 그래서 텍스트 우선(text-primary)으로 고치고 부적합 이미지 분류기를 게임결과에서 떼어냈다.

그런데 사용자가 결정적 단서를 줬다 — **"같은 스크린샷을 다른 OCR 사이트는 거의 다 맞혔다. 작으면 일정 크기로 확대하는 것 같더라."** 내가 "해상도가 근본 원인"으로 몰아간 가설이 틀렸고(작은 이미지가 못 읽을 만큼 작은 게 아니라, 우리가 원본을 그대로 Claude Vision에 보낸 게 문제), **OCR 전에 가로 ~1400px로 업스케일**하니 같은 444px 스크린샷에서 챔프 ~0/10 → 9~10/10, 닉네임 10/10으로 극적으로 개선됐다. 커밋 `8d5eb88`(이후 병렬 커밋에 일부 섞임).

### 2차 — 선수 매칭 강화 (alias + 로스터 소거 + 별칭 표시)

`matchRiotIdScored`가 별칭(alias) 매칭 단계를 이미 갖고 있는데 호출부가 별칭을 안 넘겨 죽은 코드였다. 이미 문서에 박힌 `scrimPlayerAliases` 설계를 따라:
- 별칭 맵을 로드해 매칭에 전달(죽은 코드 활성화).
- **합의/승격 시 서버가 "OCR 원문 → 선수" 별칭을 자동 저장**(단일 시청자 오보정 오염 방지 — 검증된 데이터만 학습). 추론/미확정 행은 학습 제외하는 오염 가드도 같이.
- **로스터 소거 추론**: 팀 4/5가 확정되면 남은 1명을 로스터 빈 포지션으로 추정해 후보(노란불)로만 제안(자동확정 X).
- 매칭된 선수명/후보를 **별칭(nickname)으로 표시**(예: chzzkName "MaRin마린" → "마린"). 단 매칭 키는 chzzkName 유지.
- 곁들여 **포지션 표준화**(OCR의 ADC/Jungle/Support → 표준 Bot/Jng/Sup)와 합의 매칭의 잠재 버그(ADC vs Bottom)도 정정.

firestore.rules에 `scrimPlayerAliases`(public read / 서버 쓰기)를 추가하고 production에 배포했다.

### 3차 — 수치 타당성 검산

KDA/골드/딜 status가 "전체 이미지 confidence 하나"에 일괄 종속돼, 저해상도 한 장이면 멀쩡한 수치 10행이 전부 노란불이던 것을 **값 단위 타당성 검산**(KDA 0~40, 골드 0~40k, 딜 0~200k — 주로 OCR 자릿수 오류)으로 교체. 정상 범위면 자동, 범위 벗어난 셀만 검토. 팀 합계 cross-check는 LoL 역할 변동성(서폿 5k vs 캐리 25k)이 커서 일부러 제외.

### 4차 — 자가개선 재학습 인프라 (밴 분류기 학습 루프 "소비")

캡처(보정 시 `banClassifierMisses`에 실 crop+정답 저장)는 이미 동작 중인데 **소비(재학습 투입)**가 비어 있었다. `download-misreports.mjs`(Firestore miss → 로컬 학습 데이터) + `2-augment-dataset.py`에 실 miss를 가중치 50배로 합치는 통합 + 재학습 절차 문서화. 실 miss 8건(Ornn×4 약점) 다운로드까지 검증. 실제 retrain은 venv가 필요해 인프라만(결정). 보안 리뷰가 잡은 path traversal(미스 championKey가 시청자 통제 입력)도 영숫자 검증으로 막음.

### 5차 — 밴 분류기 품질 eval → ROI 로딩 화면 대응

배포된 밴 분류기를 실 픽밴 4장에 돌려 보니 **분류기는 우수(ROI 정확 시 19/20)지만 ROI 검출이 ~절반에서 실패**해 0 인식. 원인은 사용자가 올리는 화면이 대부분 **로딩 화면**("장비를 준비하세요")이고, 밴이 상단 가로 스트립인데 그 아래 선수 카드 행도 좌우 대칭이라 휴리스틱이 헷갈리던 것. 세 겹으로 고침:
- 휴리스틱(`detectBanRois`): "상단 영역의 좌우 대칭 밴 쌍 중 최상단" 선택, 애매하면 null로 Vision에 위임(잘못된 ROI로 fallback 막지 않는 게 핵심).
- Vision 프롬프트: 세로 컬럼 → **가로 밴 스트립**으로 재작성(cropSlot이 너비를 5등분하므로).
- 숨은 함정: vite dev 미들웨어가 `type='pickban'` 라우팅을 안 해 **픽밴 Vision fallback이 dev에서 한 번도 동작 안 했음** → 라우팅 추가(prod parity). 커밋 `49fe3bf`.

## 결과

- **게임결과:** 같은 444px에서 챔프 ~0/10 → 9~10/10, 닉네임 10/10, 정상 수치 노란불 해소. 선수 매칭은 별칭/로스터/학습 루프까지.
- **밴 인식:** 실 픽밴 19/39 → **34/39(87%)**, 정상 해상도(1224px+)만 보면 35/39(90%).
- **확대 eval(6장)에서 새 발견:** 작은(820px) 픽밴은 0/10 — ROI는 Vision이 잘 찾는데 분류기가 한계(아이콘 ~27px). **업스케일도 미미** — 게임결과 *텍스트*는 업스케일로 살지만 밴 *이미지 분류*는 안 산다(중요한 대비). 즉 밴은 최소 해상도(~1000px+)가 필요.
- **검증:** 단위 회귀 580 통과, build OK, 브라우저 end-to-end, console 0. firestore.rules 배포 완료.
- **남은 것:** 정상 해상도의 분류기 miss(오른·말자하 등)는 재학습 인프라가 누적 miss로 메꿀 대상. 작은 픽밴은 경고 또는 한계 수용.

### 프로세스 교훈

1. **사용자가 명시한 fact를 가설보다 우선.** "같은 스크린샷"이라고 일찍 말해줬는데 "해상도가 원인"으로 몰아가 한참 돌아왔다.
2. **CV 휴리스틱은 계측 후 고친다.** 밴 ROI를 추측으로 두 번 회귀시킨 뒤, 밝기 프로파일을 계측하고서야 "선수 행도 대칭 밴" 진짜 원인을 찾았다.
3. **신뢰 경계 밖 데이터를 파일 경로에 쓰면 항상 검증**(보안 리뷰의 path traversal).
4. (운영 메모) 이 세션 작업이 병렬로 도는 stats/shell 커밋에 자주 섞여 들어가 커밋 메시지가 내용과 안 맞는 경우가 있었다 — 미커밋 변경을 빨리 분리 커밋하는 게 안전.
