# 메모리 (Memory)

> Claude 가 **세션 간에 인계하는 영구 컨텍스트**. 파일 기반 — `~/.claude/projects/<slug>/memory/` 에 markdown 으로 박힘. 4 종 (user / feedback / project / reference) 으로 분리.

## 한 줄 정의

**"이 사용자 / 프로젝트는 이런 룰을 따라" 를 다음 세션에도 전달하는 시스템.** [[90_AI/claude/개념/에이전트\|에이전트]] 의 한계 (세션 격리) 를 보완.

## 위치

```
~/.claude/projects/<slug>/memory/
├── MEMORY.md                    ← 인덱스 (항상 컨텍스트에 박힘)
├── user_<name>.md               ← 사용자 정보
├── feedback_<name>.md           ← 작업 룰 / 취향
├── project_<name>.md            ← 프로젝트 상태
└── reference_<name>.md          ← 외부 시스템 link
```

`<slug>` = 작업 디렉토리 mapping. pickzzk = `-Users-hikaru-workspace-pickzzk`.

> [!info] MEMORY.md 만 항상 박힘
> 본문 파일은 description 기반으로 필요 시 [[90_AI/claude/개념/에이전트\|에이전트]] 가 읽음. MEMORY.md 의 인덱스 line 이 "어떤 메모리가 어디 있는지" 안내.

## 4 종 분리

### 1. `user_` — 사용자 정보

> 사용자의 역할 / 목적 / 지식 / 선호. "이 사람은 어떤 사람인가" 컨텍스트.

예 (pickzzk):
- `user_role_viewer.md` — "user 는 시청자임 (운영자 아님 / 방송 안 함 / 시청 재미용)"
- `user_email.md` — `hikaru2016@gmail.com`

### 2. `feedback_` — 작업 룰 / 취향

> 사용자가 박은 룰 / 정정 받은 패턴. "다음에도 이렇게 박아" 의 출처.

각 entry 는:
- **룰** (한 줄로)
- **Why** (출처 사례 / 이유)
- **How to apply** (적용 시점 / 조건)

예 (pickzzk):
- `feedback_decision_one_at_a_time.md` — "결정은 한 번에 하나씩 물어봐"
- `feedback_use_libraries.md` — "외부 라이브러리 먼저 검토, 직접 구현 default X"
- `feedback_visual_check_self.md` — "Playwright MCP 로 직접 보고 검증"
- `feedback_no_uid_display.md` — "uid UI / console 노출 X"

### 3. `project_` — 프로젝트 상태

> 진행 중인 상태 / 결정 / 회의 결과. **상대적으로 빨리 stale 됨**.

각 entry 는:
- **사실 / 결정** (한 줄)
- **Why** (배경)
- **How to apply** (다음 작업에서 어떻게 활용)

예 (pickzzk):
- `project_v2_schema_lock_2026-05-08.md` — v2 schema 결정 lock
- `architecture_decisions.md` — Firebase Auth roles[] / streamers 마스터 DB / 치지직 비공식 API

### 4. `reference_` — 외부 시스템 link

> 외부 자료 위치 안내. "Linear 프로젝트 INGEST" / "Grafana 대시보드 X" 같은.

## MEMORY.md 형식

```markdown
# Memory Index

- [프로젝트 목적 및 방향](project_context.md) — 한 줄 hook
- [UI 패널 용어](terminology.md) — 좌측/우측 정의
- [pickzzk 비전](draftpick_vision.md) — 타겟 / 우선순위
- ...
```

> [!warning] 200 줄 넘으면 truncate
> Claude 컨텍스트에 박힐 때 200 줄에서 잘림. 인덱스 line 짧게 유지.

## 박는 시점

| 상황 | 어떤 종류? |
|---|---|
| user 가 새 룰 박음 ("이렇게 해줘") | `feedback_` |
| user 정정 받음 ("아니 그게 아니라") | `feedback_` |
| 큰 결정 합의 ("v2 schema 박자") | `project_` |
| 사용자 정보 알게 됨 ("나는 X 임") | `user_` |
| 외부 시스템 위치 안내 | `reference_` |

## 박지 말 것

> [!warning] 박지 마라 — 짜증 / 안 좋은 평가
> "user 가 자꾸 같은 거 물어봄" 같은 부정적 메모 X. 사용자에게 도움 안 됨.

> [!warning] 박지 마라 — 코드에서 파생 가능한 것
> 파일 위치 / 구조 / commit history / 함수 시그니처 등은 git / 코드에서 가져옴. 메모리 박을 필요 X.

> [!warning] 박지 마라 — 일시 상태
> "지금 작업 중인 commit" / "이 세션의 임시 결정" 같은 ephemeral. tasks / plan 으로 추적.

description: 결정은 한 번에 하나씩 물어봐. 묶음 / 5 option 동시 X.

---

"먼말이야 알아듣게 말해" 라고 함. AskUserQuestion 1 step 단위로 박음.

**Why**: 2026-05-04 회의 / 2026-05-13 C14d 재확인. user 가 "그냥 너가

**How to apply**: 큰 decision 박을 때 plan MD 박고, 첫 결정 1 개만 AskUserQuestion.

## 헷갈리는 점

> [!warning] 메모리 ≠ 대화 컨텍스트
> 대화 컨텍스트 = 1 세션 안에서만 보존. 메모리 = 세션 간 영구.

> [!warning] feedback_ vs project_
> - **feedback_** = 작업 패턴 / 룰. 거의 영구
> - **project_** = 프로젝트 상태. 빨리 stale → 정기 갱신
> 헷갈리면 feedback_ default.

> [!warning] 메모리 박힌 fact ≠ 현재 사실
> 메모리는 박힌 시점의 사실. 6 개월 후 stale 가능. 의심되면 코드 / git 으로 verify.

> [!warning] 너무 많이 박으면 노이즈
> 1 사용자 / 프로젝트 = ~20~50 entries 가 적정. 너무 많으면 인덱스 줄 truncate + invoke 비용 ↑.
